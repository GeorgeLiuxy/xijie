# Private post, person and gift journey photos

Media is an independent TypeScript/Nest service on `127.0.0.1:3106`, with its own PostgreSQL database and migration history. It stores ownership, upload slots, canonical media, purpose-specific bindings and durable processing/cleanup work. Private bytes live in S3-compatible storage. Identity owns permissions; Social, People and Gifts own their respective source references. Media calls them over authenticated HTTP and never queries another domain's database.

This slice supports JPEG, PNG and WebP input up to 10 MiB / 32 million pixels per image, and 1–9 images per original post flow. An image-only post is supported by Social. Images are never sent to AI. Unknown types, malformed images and animated inputs are rejected without a fake successful upload.

## Dependencies and configuration

Reuse NestJS 11, `pg`, official AWS SDK v3 `@aws-sdk/client-s3@3.1168.0` and `sharp@0.35.5`. Sharp actually decodes, applies orientation, strips metadata and encodes a non-enlarged WebP of at most 2048 pixels on its longest edge and 1 MiB. It lowers dimensions/quality within that bound; an image that still cannot meet the bound is rejected.

All required variable names are in `.env.example`. Local private values belong in ignored `.tmp/media-dev/server.env`. The Media service token, accepted Social/People/Gifts tokens, data-rights token and `MEDIA_READ_PROOF_KEY` are independent credentials. API and Worker share the Media database and private object-store settings. Neither process loads model credentials. The configured bucket must already exist and deny anonymous access.

```powershell
Set-Location -LiteralPath 'D:/AI/xijie figma/backend/services/media'
pnpm install --frozen-lockfile
pnpm build
node --env-file=../../../.tmp/media-dev/server.env dist/migrate.js
node --env-file=../../../.tmp/media-dev/server.env dist/main.js
# A separate background process:
node --env-file=../../../.tmp/media-dev/server.env dist/worker.js
```

Migrations `001_media.sql`, `002_person_photos.sql` and `003_gift_delivery_photos.sql` are applied in order. Applied files are checksum-checked and must not be edited after application. The Worker claims persistent database work with leases and `FOR UPDATE SKIP LOCKED`; restart does not imply a successful image. It retries temporary object-store failures, uses independent immutable keys for processing attempts, and validates the current exact upload authorization before committing a derived image.

## Public operations

The authoritative shared slice is [private photo implementation](../../../docs/backend-api/identity-people.md#r01-私人空间配图实施基线2026-11-13). Responses are `{data: ...}`; errors follow the existing `{error:{code,message,requestId}}` envelope.

| Operation | Contract |
| --- | --- |
| `POST /v1/media` | `{mimeType,byteSize,sha256,purpose:'post_attachment',target:{kind:'post_intent',id:clientPostId}}`. Returns `{media,upload}` with a same-origin PUT URL and required `Content-Type`. |
| `PUT /v1/media/{id}/uploads/{slotId}` | Exact declared raw bytes, current session, expected session, Origin and stable upload idempotency key. Rejects digest/length/type mismatch and expired or replaced slots. |
| `POST /v1/media/{id}/complete` | `{uploadSlotId}` and stable completion key; returns `202 MediaDTO`. `verifying` progresses to actual `ready` or `rejected` in the Worker. |
| `POST /v1/media/{id}/upload-slots` | Explicit new-slot intent and `If-Match`. Retires the old slot and uses a new private staging key; old slots cannot complete the replacement. |
| `GET /v1/media/{id}` | Owner metadata and current state, without storage keys. |
| `POST /v1/media/{id}/read-url` | `{purpose:'post_attachment',target:{kind:'post',id}}`. Returns `authorized_stream`, fixed relative content URL, expiry, authorization version and a 60-second HMAC proof bound to the session and exact media/post/permission versions. |
| `GET /v1/media/{id}/content` | Cookie, Expected-Session and `X-Media-Read-Proof`. Rechecks permission, binding and current Social source before and after loading exact bytes. `image/webp`, `no-store`, `nosniff`. Ranges are not enabled in this image slice. |
| `DELETE /v1/media/{id}` | Stable key and `If-Match`; revokes reads immediately and schedules physical cleanup. Owner deletion remains possible after photo permission withdrawal. |

Current `storyStorage.allowed && privateFeedAllowed===true` and the independent `photoStorage.allowed` are required for upload, publication and normal image reading. A later grant can reopen a ready, still-owned image; it cannot resume an old upload slot or verification task under another captured grant. Storage withdrawal and deletion are separate actions. Metadata and formal data-rights processing do not pretend withdrawal deleted the bytes.

## Cross-service binding and cleanup

Only Social's credential can invoke `POST /internal/v1/social/posts/{postId}/media-bindings` with account header and `{clientPostId,mediaIds}`. Media atomically verifies and binds the complete ordered list. Each association has a 1-based position, preserves the original post intent and cannot be reused on another post. Same-post/same-list retry returns the same bindings. A prebinding cannot be read before Social commits its authoritative post.

Media uses its own credential to call Social `POST /internal/v1/media/posts/validate {refs:[{postId,mediaId,version}]}`. This source API returns only metadata; Media enforces the user's current photo permission separately. A deleted post immediately invalidates old read proofs even before object deletion. Social's `media-release` is idempotent; Worker source reconciliation also catches unavailable/abandoned targets after the 15-minute commit grace period. Remote errors never count as a confirmed deletion.

Source reconciliation rotates using a dedicated check timestamp, without changing content versions. Original input cleanup records progress on upload slots and retries transient failures. An old upload attempt never deletes its slot's shared staging object; only terminal-slot cleanup and erasure do. Purge work records each successful input deletion and lists remaining canonical objects so retry can make progress across leases. Cleanup retries are not capped at the image-verification attempt limit.

## Person photos (K02)

The original optional six-photo selection uses `purpose:'person_photo',target:{kind:'person_draft',id:draftId}` for both create and read-url. Confirmation does not move or duplicate the media target; People resolves the stable source draft to the current active person. `storyStorage.allowed` and independent `personPhotoStorage.allowed` are required. The private-space photo grant and `privateFeedAllowed` do not authorize or block this separate purpose. `private_person_photo_storage` v1 covers private save/display/export only, never model input. Migration `002_person_photos.sql` adds the independent target/grant records without changing applied migration 001.

People alone calls `POST /internal/v1/people/drafts/{draftId}/media-bindings {mediaIds}` with its own credential and account header. Up to six exact ready images must belong to that same account/draft/purpose. Response `{draftId,expiresAt,media}` preserves input order. `expiresAt` is a 60-second precommit lease: People checks it inside its final source-reference transaction. Candidate grants are additive, so a failed or racing edit cannot revoke the previously committed list. Only People maintains authoritative positions.

Media validates the target via `GET /internal/v1/media/people/drafts/{draftId}` and current references via `POST /internal/v1/media/people/validate {refs:[{draftId,mediaId,version}]}` using its own service credential. Reads revalidate exact current references before bytes are delivered, so replacement/removal immediately blocks old proofs. A changed or expired draft/person rejects new uploads and late processing. Photo consent withdrawal independently stops new work/reads and never blocks data rights.

Person cleanup requires source-invalid evidence and a 15-minute grace after the latest prebind. The same timestamp is rechecked under the Media account gate before revocation, protecting a newer concurrent bind; the shorter People commit lease rules out arbitrarily delayed commits. Remote errors are not deletion evidence. Direct deletion of a bound person image returns `MEDIA_IN_USE`: the user removes it through the authoritative People list, after which source reconciliation owns physical cleanup. Private bytes and all new grants participate in account erasure. Configure `XIJIE_PEOPLE_URL` and accepted `XIJIE_PEOPLE_SERVICE_TOKEN` independently; missing configuration fails closed for this purpose.

Person exports add `personBindings` with stable draft targets; the People export provides authoritative order. Source-invalid person photos are omitted. Consent withdrawal does not block the actual-byte export or erasure.

## Gift journey photos (R02)

The original completed journey animation produces a single canvas capture. Rewatching may replace that image through Gifts' independent photo resource. Create and read-url use `purpose:'gift_delivery_photo',target:{kind:'gift_delivery',id:deliveryId}`. Media requires current `giftStorage.allowed` and independent `giftPhotoStorage.allowed`; neither story storage, person/space photo permission nor AI authorization is required. The target must be an owned, readable, server-arrived delivery. Media never changes arrival state, delivery version, return jobs or balances.

Migration 003 adds `gift_delivery_id`, `gift_storage_authorization_version` and `media_gift_grants`. Gift rows use the explicit gift storage authorization field and leave the old story storage field null. The accepted gift photo grant is independent of the gift storage grant. Finished currently referenced photos can be read after regrant using a new proof, but old upload slots, slot renewal and queued verification work cannot be revived under changed captured versions. An unfinished ready capture also cannot first bind under a new grant: it returns `PHOTO_SELECTION_INVALID`. Rebinding a saved image after regrant requires an exact still-current source reference.

Only the Gifts service credential can call `POST /internal/v1/gifts/deliveries/{deliveryId}/media-bindings` with `X-Xijie-Account-Id` and `{mediaId,photoVersion}`. The intended next Gifts photo version is at least 2. The response is `{deliveryId,photoVersion,media,expiresAt}`, with a 60-second commit lease checked by Gifts inside its final transaction. Bindings are additive by `(account_id,media_id,photo_version)`: an abandoned or racing replacement cannot revoke the current source. The separate Gifts photo version never changes the outgoing delivery DTO/version.

Using its own credential, Media calls `GET /internal/v1/media/gifts/deliveries/{deliveryId}` for `{deliveryId,accountId,status:'arrived',photoVersion}` and `POST /internal/v1/media/gifts/validate` with `{refs:[{deliveryId,photoVersion,mediaId,version}]}`. These source checks are independent of normal consent. Reads require an exact active grant and current four-field reference. The read proof adds `sourcePhotoVersion` for the source resource version and `giftStorageVersion`; its existing `photoVersion` continues to mean the selected photo permission version. Replacing the photo invalidates old proofs even when the same media is later selected again.

Source-invalid candidates are collected only after the 15-minute grace following the latest prebind, with its timestamp rechecked under the account gate. A still-valid candidate protects the canonical object. Dependency outages are not deletion evidence, and an active binding rejects direct media deletion with `MEDIA_IN_USE`. Export includes only current gift photo references, `giftBindings` and actual canonical bytes, rechecking references after reading bytes; withdrawal does not deny export. Erasure removes staged and finished objects and every gift grant. The recovery verifier connects restored Gifts photo rows to same-owner arrived deliveries, active People sources, exact grants, metadata and verified object hashes; removed source history may outlive collected bytes. Configure `XIJIE_GIFTS_URL` and `XIJIE_GIFTS_SERVICE_TOKEN` independently; absent configuration fails closed for this purpose.

## Chat photos (R01)

`conversation_attachment` uses the immutable target `{kind:'conversation_message',id:clientMessageId,conversationId}`. Independent `chatPhotoStorage` supplements current `storyStorage`; existing space/person/gift photo grants do not authorize it. Upload, slot renewal, completion and verification check captured account/story/photo versions. Regrant can read a still-current saved image with a new proof, but cannot revive an old unfinished upload or first-bind an old ready candidate. Conversations separately requires `chatImageReplies` to accept a photo and creates its independent visual reply job.

Migration 004 adds `chat_conversation_id`, `chat_client_message_id` and `media_conversation_grants`. Native constraints keep purposes exclusive and lock each grant to its account, media, conversation, client message, original message version 1 and immutable media version. One client message has one image; replacement is a new send intention. API and Worker require this schema before starting.

Only the Conversations credential may call `POST /internal/v1/conversations/:conversationId/messages/:clientMessageId/media-bindings` with `{mediaId,version}` and the account header. The response contains target IDs, canonical metadata and a 60-second `expiresAt`. Conversations checks that deadline under its own SQL lock before committing message, relation, job and permanent receipt. Network calls never join the local transaction. Candidate bindings alone cannot authorize reads, and failed/racing binds cannot revoke another valid source.

Media uses its own credential for `GET /internal/v1/conversations/:id/photo-target` and `POST /internal/v1/conversation-media/validate`. Validation accepts up to 100 exact `{conversationId,clientMessageId,messageVersion,mediaId,version}` references and receives a same-length boolean vector. Sources check account/person existence and a live direct message independently of photo consent, so withdrawal is not deletion evidence. Browser read-url uses the upload target; its HMAC proof additionally binds `conversationId`, `clientMessageId` and `sourceMessageVersion`. Existing `photoVersion` remains the photo permission version. Reads recheck committed source and permissions before and after byte IO.

`POST /internal/v1/photo-reply-jobs/:jobId/attempts/:attemptId/media-content` accepts an empty body and only the Conversations credential/account header. It returns canonical WebP bytes, never a storage URL or browser proof. Media calls the exact Conversations `media-source` attempt endpoint before and after IO and verifies captured account/story/photo/image permission versions and current message/media association. Changed or missing attempts fail. Normal browser photo reads do not require AI permission; Media does not call a model.

Source-invalid images retain the 15-minute prebind grace and locked timestamp check; outages cannot trigger cleanup. Active grants reject direct deletion with `MEDIA_IN_USE`. Removing the owning message immediately invalidates reads and later permits GC. Export adds `conversationBindings` and actual canonical bytes only for valid committed sources, rechecking after IO; withdrawal does not block rights. Erasure covers the new grant table and both object prefixes. Configure `XIJIE_CONVERSATIONS_URL` and `XIJIE_CONVERSATIONS_SERVICE_TOKEN`; absent configuration fails closed.

## User-provided person voice samples

Migration 005 stores real recorded or selected audio separately from photos and live AI calls. This purpose needs current story storage plus the independent `private_person_voice_storage` decision (Identity028). It stores and plays the original voice after format normalization; it never sends the sample to a model, clones a voice, or changes it to match tone/timbre preferences. Those preferences are separate explicit People fields. Ordinary photos remain available when `MEDIA_FFMPEG_PATH` is unset. A configured decoder must be an absolute, regular, non-symlink file; configuration preflight reads file metadata without executing it. Missing configuration rejects sample creation with `AUDIO_DECODER_UNAVAILABLE`.

`POST /v1/person-voices` accepts declared MIME, byte count, SHA-256 and `{kind:'person_draft',id}`. Allocation, raw PUT, completion and explicit expired-slot renewal retain the original asset/hash and permanent request keys. GET is read-only. An unknown PUT probes the original staging key; renewal never replaces an uploaded original. Input is at most 8 MiB and 30 seconds. A bounded, pipe-only ffmpeg process decodes WAV, MP3, Ogg/WebM Opus and MP4/AAC into deterministic mono 24 kHz PCM WAV (at most 1,440,044 bytes), rejecting forged formats, absent audio and excessive duration. Durable leased jobs bound retries and fence lost permission, source removal and late attempts. An absent decoder or failed decode never reports ready.

People prebinding captures its current source epoch and an exact persisted 60-second expiry. People rechecks both under its source writer lock. A candidate alone cannot play: proof/content require the current committed same-owner People binding and its monotonic binding version. A same-voice unlink/rebind invalidates the earlier proof. DELETE needs owner session/CAS/permanent key but no renewed storage grant or live target. A still-bound voice returns `VOICE_STILL_BOUND`; a live or concurrently renewed prebind returns `BINDING_IN_PROGRESS`. After an acknowledged unlink/replacement, its advanced source epoch permits immediate cleanup. Accepted-delete retries remain permanent. The response reports revocation while durable cleanup removes both private staging and canonical prefixes; it does not claim that object deletion has already completed.

`GET /v1/person-voices/create-commands/:key` exposes only owner asset ID, version, status and original target for safe unknown-allocation cancellation, even after permission/target loss. A version conflict on DELETE supplies the owner-only current version. Neither endpoint issues a playback proof. Unbound ready candidates receive a bounded orphan grace, and dependency failures never prove source removal. Export distinguishes current person bindings, unbound owned bytes and unverified uploaded originals; withdrawal does not deny data rights. Erasure fences first and verifies both real object prefixes empty. Recovery preserves exact accepted intent, historical notice-bound grants, canonical manifest/hash and People epochs, then irreversibly blocks restored sample execution. Live-call grants are destroyed and active calls fail explicitly without invented call duration. A recovered copy remains unavailable for release until the separate recovery policy is satisfied.

Isolated verification includes actual PostgreSQL schemas, private S3 objects, real ffmpeg output and Nest HTTP. It covers browser audio containers, fake MIME/no-audio/overlong input, lost responses, expired slots, permission changes, source ABA, binding/deletion races, real byte export/erasure, canonical/raw recovery manifests and metadata-only decoder preflight. These checks do not establish production storage deployment or physical microphone capture on every device.

## Export, erasure and recovery

Data-rights endpoints use the existing independent receipt credential and Identity request context. Export includes actual canonical WebP bytes as base64, SHA-256, media metadata, bindings and non-secret processing metadata. The 20 MiB domain JSON bound fails explicitly with `EXPORT_TOO_LARGE`; it does not truncate an archive or return only image IDs. Photos whose committed Social source has disappeared are omitted. Regranting photo storage is not required to copy existing data through these rights endpoints.

Account erasure first fences all new writes and reads. It waits for accepted upload/processing IO, removes both account object prefixes and verifies they are empty, then deletes the owned rows and completes its receipt. An object-store failure leaves a preparing receipt for retry. Historical requests and erasure fences remain controlled by their owning domains. Restoring the Media database alone does not restore photos: encrypted object bytes, manifests and hashes must also be restored in an isolated target before claiming a photo recovery drill passed.
