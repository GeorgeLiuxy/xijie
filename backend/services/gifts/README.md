# Trial assets and private gifts

Gifts is an independent Nest service at `127.0.0.1:3107`, owning its PostgreSQL database, catalog, trial and promotion lots, append-only ledger, referral reward receipts, delivery receipts, received gifts, gift notifications, journey-photo references, durable jobs and Outbox. Identity owns the separate `virtual_gift_storage`, `person_gift_returns` and `gift_delivery_photo_storage` permissions; People owns current recipients and authorized return context; Conversations owns stable gift-card references; Media owns private image bytes. HTTP and model calls occur outside SQL transactions. Real AI returns are implemented behind an explicit switch and synthetic-account allowlist, disabled by default. Real payment channels and OS push remain outside this slice.

The catalog is a versioned copy of the original gift definitions, preserving display names, product copy, category, price in postage units and artwork selectors. Existing unavailable, scene, service, build and fuel items cannot be sent through this slice. Free crane/card gifts still receive unique delivery receipts without zero-unit ledger records. One request spends trial postage, the exact inventory item, or one eligible basic voucher. Vouchers use `assetId=return-stamp`; eligibility is one available prop/keepsake worth 1–8 postage. Quantities are 1–99 and nonstackable items require one. A trimmed note is at most 120 Unicode code points.

`POST /v1/gift-deliveries` uses the current session, expected-session header, registered Origin and UUID Idempotency-Key, with `{personId,giftId,catalogVersion,quantity,source:'trial'|'inventory'|'voucher',note}`. The permanent acceptance key and normalized input fingerprint outlive temporary HTTP caches. Replay cannot change the selected source or reprice a committed delivery. The account gate serializes competing spenders; lots are locked in stable UUID order and spent by expiry, issuance and UUID. Current database time is checked after locking. A transaction creates debit entries, updates lot balances, validates a ledger rebuild, saves the receipt, enqueues work and records Outbox events together. Separate received-gift and notification writes are described below.

Reads are `GET /v1/gift-catalog`, `/v1/wallet`, `/v1/wallet/ledger`, `/v1/gift-deliveries`, and `/v1/gift-deliveries/{id}`. Catalog supports person/category filters and ID pagination; delivery lists support person/status/displayable filters and stable receipt cursors. Catalog metadata adds `unitPostage`, `acceptsVoucher` and `availableSources`. Wallet GET never grants assets or imports browser data. Normal responses contain no credentials. The full delivery DTO includes immutable `giftSnapshot` and `personSnapshot`, actual `status`, planned/actual times, original debit and reversal references, and nullable `failureCode`.

People is checked through its authenticated Gifts metadata endpoint. Conversations ensures one direct chat before Gifts accepts a receipt. This does not create a cross-database transaction: a failed acceptance may leave an empty private chat, but no debit or fake gift card. Worker acceptance projections and arrival projections independently retry through Conversations. Its source read, `GET /internal/v1/gifts/deliveries/{id}?accountId=...`, accepts only the Conversations credential, rechecks current ownership/permission/person, and rejects captured authorization-version changes. Projection failures never cause duplicate debits or turn an arrived delivery into a failure.

Deliveries progress `in_transit → arrived / delivery_failed` only in Worker transactions. The eight-second schedule is a server-side plan; client clocks never mark arrival. Missing recipients and changed/withdrawn gift permission deterministically fail still-pending deliveries with an inverse of each original debit line, at most once. Network errors remain retryable. Regrant cannot restart an old delivery or recreate its old-authority chat card. Reversal preserves the original lot and expiry; an expired refunded lot remains unavailable. Only account erasure removes trial ledger facts. No automatic ledger repair, price-based refund or synthetic persona reply exists.

## Real AI returns and received gifts

`002_person_gift_returns.sql` adds captured return/story authorization versions to new deliveries and creates `gift_return_jobs`, `received_gifts`, `gift_received_projection_jobs`, `gift_notifications` and permanent `gift_mutation_receipts`. Apply Identity `012_person_gift_returns.sql` and Conversations `008_received_gift_cards.sql` with their service deployments. Existing published policies and grants do not authorize this new purpose. New gift acceptance captures the exact current `giftReturns`, `storyStorage`, `giftStorage` and account-access versions; absent return permission does not prevent ordinary sending, and a later grant does not backfill history.

The delivery worker creates eligible return work only after an actual `arrived` commit. A separate `dist/return-worker.js` runs generation and incoming-card projection. `GIFTS_AI_ENABLED` defaults to false. Enabling it still requires nonproduction execution, explicit synthetic UUIDs in `MODEL_ALLOWED_ACCOUNT_IDS`, `MODEL_BASE_URL=https://api.openai.com/v1`, `MODEL_NAME`, and a private `MODEL_API_KEY`. The fixed SDK versions are `ai@7.0.169` and `@ai-sdk/openai-compatible@3.0.90`; the provider uses `store:false`, no SDK automatic retries and a 30-second request timeout. The allowlist is an additional deployment restriction, not user consent. Credentials and raw model input are never logged.

Only the source gift, quantity, note, a bounded catalog and People-provided name/relationship/called-me/story context enter the model. Photos, chat history, treasures, automatic memories and movement history are excluded. Current permissions, source version, person version and world version are checked before and after generation; a 90-second attempt lease fences local commit. Return jobs have at most three attempts, including expired leases. Withdrawal or version changes block old work; regrant does not revive it. Cross-domain checks are HTTP boundaries, not atomic cross-database revocation.

The model decides either `{decision:'none'}` or `{decision:'gift',giftId,note}`. `none` is a persisted successful decision with no received gift or received notification. A gift must be an available person-compatible keepsake/prop, quantity is always one, and its note is at most 120 Unicode code points. Invalid output or model errors never fall back to a template. The source delivery and generation job are each unique for the received result; model/response provenance stays in private generation facts, not the public card. Returns never credit postage, vouchers or spendable inventory and never trigger another return.

`GET /v1/received-gifts` and `GET /v1/received-gifts/{id}` return the authoritative received DTO. `POST /v1/received-gifts/{id}/open` records the first server `openedAt` and `placement=record`; a repeated open preserves an existing space placement. `PATCH /v1/received-gifts/{id}` accepts `placement:record|space`, requires an opened and eligible object, and uses `If-Match`. Opening the original received-detail UI invokes open; the original unopened card already displays gift name and note. `GET /v1/notifications` provides separate total/unread counts; `PATCH /v1/notifications/{id}` with `{read:true}` and `If-Match` marks only the notification read, without opening a gift. All writes require the original session, Origin and permanent idempotency key. Accepted replay returns current state plus accepted-version metadata rather than overwriting a later choice.

Ordinary received reads and source projections require the original captured authorization versions as well as current permissions and a live source/person. The Conversations-only source is `GET /internal/v1/gifts/received/{id}?accountId=...`; `PUT /internal/v1/gifts/received/{id}` in Conversations updates one incoming card. Notifications are deduplicated by account/type/source event and hold resource references; opening their target rechecks current access. Notification reads do not substitute stale content for an inaccessible object.

## Journey photos

`003_gift_delivery_photos.sql` introduces an independent photo resource and permanent `gift_photo_commands`. Apply Identity013 and Media003 with their service deployments. Configure `XIJIE_MEDIA_URL` and the distinct `XIJIE_MEDIA_SERVICE_TOKEN` together; both may be absent to preserve an existing Gifts deployment, in which case new photo endpoints return `DEPENDENCY_UNAVAILABLE`. This feature needs current `giftStorage` and independent `giftPhotoStorage`, not AI-return or ordinary AI permission. Existing grants do not expand to this purpose. Current saved photos become readable after regrant; uploads captured under an old permission version cannot resume under a new grant.

`GET /v1/gift-deliveries/{id}/photo` returns `{deliveryId,version,photo,updatedAt,origin:'journey_capture'}` and a photo-specific ETag. Before any save it returns version 1, `photo:null` and the receipt creation timestamp without writing a row. `PUT` at that path accepts only `{mediaId}`, the expected session, registered Origin, permanent UUID `Idempotency-Key` and photo `If-Match`. First save creates version 2; replacement advances only the photo version. An accepted old-key retry returns the current photo without rebinding an obsolete image or overwriting later work. `GET /v1/gift-delivery-photos` uses receipt-ID cursors and immutable receipt creation ordering; removed recipients are filtered while the cursor still progresses.

The approved source is the completed journey animation's canvas capture for a currently arrived delivery. Normal reads and writes recheck active ownership and person, with permission checks before and after the operation. Only IDs and normalized WebP metadata are saved, with no URL or image bytes. Media prebind is called outside SQL locks with the proposed next photo version. The account-locked transaction rechecks arrival, current photo version, erasure fence and the 60-second binding expiry against database time after lock waiting. Binding failures preserve the old image. Captured gift lifecycle versions, receipt DTOs, arrivals, return generation, notifications, asset balances and chat sequences never change because a photo was saved.

Media-only `GET /internal/v1/media/gifts/deliveries/{id}` and `POST /internal/v1/media/gifts/validate` require the separate Media credential and `X-Xijie-Account-Id`. Validation matches the current `{deliveryId,photoVersion,mediaId,version}` reference and active source/person, independently of ordinary storage consent so withdrawal does not trigger garbage collection. Replacement or person removal invalidates the old reference immediately on the next source check. Historical command/event references do not keep replaced bytes alive. There is no public photo DELETE in this UI slice, and neither bytes nor photo references enter model input or gift chat cards.

Photos, permanent commands and photo events are covered by the existing export revision/size checks and erasure transaction; Media separately exports valid WebP bytes and removes objects behind its own fence. Restore must validate owner, immutable delivery target, purpose, photo/media versions, grant and metadata against the actual object. The photo implementation and isolated PostgreSQL/HTTP checks do not establish original-animation, live Media, browser or native recovery acceptance; that validation belongs to the root task.

## Referral rewards

`004_referral_rewards.sql` adds immutable `referral_reward_awards` and account-private `referral_reward_receipts`. The `first-memory-v1` campaign gives each inviter and qualifying new member exactly one non-expiring promotion voucher (`return-stamp`). The existing voucher source can spend this lot for one eligible 1–8 postage gift. Normal wallet reads never issue rewards or trial assets. Recording an earned benefit needs active accounts, not a private gift-storage or AI grant; normal wallet reading and spending still require the existing gift-storage permission.

Optional `XIJIE_MEMORIES_URL` enables referral reconciliation in the existing Gifts worker. Its own bounded loop uses the dedicated Gifts credential to read Identity `/internal/v1/referrals/pending?limit=20&after=...`, then the invitee's minimum Memories qualification metadata. UUID pagination rotates past ineligible candidates. Registration and the first qualifying `manual|ai_candidate` confirmation must be in order. No original memory body, person ID, or memory ID is fetched. Both account contexts are checked outside SQL; sorted account gates, two credit transactions, two lots, both private receipts, a shared award and their events commit atomically. Permanent business keys are `referral:<id>:host|guest`, and deferred native checks require both exact benefits. Concurrent attempts cannot grant a second pair.

Only after commit does the worker acknowledge Identity with `{receiptId,qualifiedAt}`. Lost acknowledgements and process restarts read the permanent award first and repeat the same acknowledgement without re-reading a now-deleted memory or issuing another voucher. Link revocation does not reverse accepted attribution or benefits. An unavailable dependency remains pending for later polling; no balance is invented. This is a cross-service receipt protocol, not a distributed SQL transaction.

Exports include only the account's own `referralRewards` receipt, lot, transaction, entries and Outbox events; shared counterparty and qualification-event identifiers are excluded. Erasing either participant removes the shared award and that account's private facts. The survivor keeps its own earned benefit without the erased party's identity. Permanent erased-account gates prevent an old attribution from issuing a replacement pair. These implementation and isolated database checks do not claim original-UI or native-recovery acceptance.

## Shared-album promotion

`005_album_rewards.sql` records one immutable `album_reward_receipts` row for each `(account_id,album_id)`. `POST /internal/v1/promotions/shared-albums/{albumId}/reward` requires the distinct optional `XIJIE_SOCIAL_SERVICE_TOKEN`, `X-Xijie-Account-Id` and an empty body. Social owns approved participation and claimant verification; Gifts accepts no client amount, source, expiry or arbitrary business key. It checks the active account and permanent erasure fence, then credits one non-expiring `promotion` voucher under `album:<albumId>:participant:<accountId>` in one transaction. The response is `{receiptId,albumId,accountId,assetType:'voucher',assetId:'return-stamp',units:1,grantedAt}`; replay returns the same receipt. `GET` on the same internal path returns that receipt or 404 without granting assets, allowing Social to resolve an earlier unknown result after withdrawal. `data.albumRewards` is exported and erased with the owner's ledger. The optional credential being absent disables this route.

## Provider-independent purchasing core — initial disabled baseline

The following describes the earlier core-only slice. The configurable self-hosted integrations below supersede its statement that runtime has no adapter. Purchasing still defaults to disabled until merchant and approved product configuration exists.

`006_commerce_core.sql` adds durable quotes, orders, payment attempts, refunds, refund reservations, normalized verified evidence, permanent close commands and reconciliation jobs. No merchant, production SKU, price or payment channel is configured. `CommerceStore` in API/worker therefore has no adapter: product reads return an empty list, purchasing reports `PURCHASE_UNAVAILABLE`, and no payment job is dispatched. There is no environment switch to activate a mock provider. The only injected adapter factory requires an explicit test object and `NODE_ENV=test`; runtime startup never calls it.

HTTP reads are `GET /v1/products`, `/v1/orders` and `/v1/orders/{id}`. Mutations are `POST /v1/purchase-quotes {productId,quantity:1,channel}`, `/v1/orders {quoteId}`, and `/v1/orders/{id}/payment-attempts`, `/close`, `/refunds` with `{}`. They require the existing real session, expected-session header, registered Origin and UUID permanent key. Quotes capture product/version and integer minor-unit currency amounts; the database checks expiry after locking. Reads never advance payment. No browser or generic service-token endpoint accepts a paid/refunded assertion.

The private adapter contract returns either pending or verified evidence tied exactly to order, original operation, provider event, transaction, amount and currency. The worker persists the operation before outbound transport. A lost response or restart only inspects that operation; it never creates a second charge. Attempts have a 45-second lease, 30-second transport bound and at most three reconciliation attempts, including expired leases. Unknown or invalid evidence remains a blocked reconciliation item with no fabricated success. Account/lease checks run again before transport and commit. Verified payment, one paid lot, its credit ledger entry and fulfillment commit together; native evidence uniqueness and source constraints reject detached evidence or forged paid state.

Only a full refund whose original issued units remain unspent can reserve automatically. `asset_lots.reserved_units` is checked against the immutable reservation source; wallets and delivery debits use `balance_units-reserved_units`. The same account gate serializes spending and refund reservation. Verified refund success captures the reserved original lots with one inverse ledger transaction; verified failure releases them. Unknown outcomes remain reserved. Consumed entitlements persist a review request and return `REFUND_REQUIRES_REVIEW`, without negative balances or a synthetic refund. Existing gift API source selection remains unchanged; individual ledger lots explicitly preserve `trial`, `promotion` or `paid` origin.

Financial retention rules are not approved. Erasure fails explicitly with `FINANCIAL_RECONCILIATION_REQUIRED` for unresolved attempts and `FINANCIAL_RETENTION_POLICY_REQUIRED` for any verified paid fact, including a refunded order. This gate precedes the erased-account fence and prevents partial deletion. Unpaid orders with no unresolved attempt can be erased with their private facts. Export includes financial records after ordinary gift-storage withdrawal. Isolated synthetic adapter tests establish state/ledger behavior only; they do not establish payment-provider, merchant, refund-channel or production financial-retention acceptance.

## Configurable self-hosted checkout (2026-11-15)

`007_jeepay_checkout.sql` adds immutable first payment links and merchant-binding hashes to original attempts, and monotonic reconciliation error counts/deadlines. Runtime uses `createCommerceIntegration(config.commerce)`: explicitly configured JeePay and Hyperswitch may run together, selected by each frozen quote's channel. Arbitrary injected synthetic providers still require isolated test mode. No official SKU, price, credentials or enabled merchant are supplied by default.

JeePay implements pinned API1.0 signed JSON requests, data-only response verification, QR_CASHIER `payurl` redirects (including `#/hub/`), signed authoritative payment/refund queries and form notifications. Hyperswitch implements pinned v1 self-hosted Payment Links, stable reversible 30-character payment/refund IDs, automatic capture, private merchant-key queries and raw-byte HMAC-SHA512 outgoing notifications. The normal `payment_link.link` opens top-level; `secure_link` requires an iframe upstream and is not used by this redirect integration. International wallet availability belongs to the configured connectors, merchant/region/currency, domain verification and device capability.

`POST /v1/callbacks/payments|refunds/jeepay|hyperswitch` does not accept a browser's paid assertion. Verification only wakes a matching existing operation for a private authoritative query. A Hyperswitch profile's single webhook may carry either signed payment or refund events. Body size is limited to32KiB, JSON raw bytes are preserved, invalid signatures do not ACK as success, and blocked/restore-review work is not revived. Payment polling is bounded to30 minutes/64 actual attempts, refunds to24 hours/1441; normal pending does not consume the independent three-error budget. Started operations are inspected after unknown results instead of reissued. Gateway/merchant/profile bindings are checked before transport and commit; keys can rotate without silently rebinding old operations.

Launch URLs stay private, expire, and are excluded from account exports. Restore checks preserve their provenance and error/deadline budgets while quarantining executable jobs. Paid postage is included in frontend spendable postage; ledger origin remains paid. Financial operations and configurable retention are described below.

See [complete private setup](../../../deploy/checkout-setup.md), [JeePay source/deployment pins](../../../deploy/jeepay/README.md), [Hyperswitch source/deployment pins](../../../deploy/hyperswitch/README.md), and [.env.example](./.env.example). These adapters and controlled PostgreSQL/HTTP/browser checks do not establish a deployed gateway, live merchant charge, wallet-device success, store billing or production release. No external payment stack was started by this slice.

## Google Play purchase verification

This operator command reads one approved, single-quantity, one-time product purchase. It checks the expected application-account binding against the [purchase lookup](https://developers.google.com/android-publisher/api-ref/rest/v3/purchases.productsv2/getproductpurchasev2). The separate [order lookup](https://developers.google.com/android-publisher/api-ref/rest/v3/orders/get) checks the same token and product and supplies final buyer money. The output includes a token fingerprint, the store order reference and the purchase status. Only a consistently processed purchase provides a total and consumption state. The command has no wallet or Play write access in code.

Build Gifts, then use a protected environment file, an expiring Publisher OAuth bearer token, and a protected request file. Acquire the bearer via your approved Google credentials with the `androidpublisher` scope. Set `GIFTS_GOOGLE_PLAY_VERIFICATION_ENABLED=true`, `GIFTS_GOOGLE_PLAY_PACKAGE`, `GIFTS_GOOGLE_PLAY_PRODUCT_ID`, `GIFTS_GOOGLE_PLAY_VERIFICATION_MODE=test` and `GIFTS_GOOGLE_PLAY_ACCESS_TOKEN_FILE` (absolute path). `test` expects Play's test marker. Use `live` only when inspecting an authorized real order. Set file permissions or Windows ACLs so only the operating account can read them.

```powershell
node --env-file=<private-env-file> scripts/google-play-verify.mjs <absolute-private-request-file>
```

The request file contains `purchaseToken` and `accountBinding`. Take `accountBinding` from the app's trusted record of the obfuscated account ID used when launching billing. Storefront setup, a native purchase flow, transactional purchase-token deduplication with the wallet, consumption after fulfillment and refund reconciliation require their own release validation. Keep this verification output private as order metadata.

## Financial operations and account erasure

`008_financial_operations.sql` adds immutable operator acceptance/audit and minimized financial archives. Identity runs the dedicated-rights-credential `POST /internal/v1/accounts/{id}/erase-preflight` before erasing any configured domain, on every retry. Its body and exact `Idempotency-Key` are the accepted `delete_account` request UUID; its Identity context must be `deletion_pending` with request `accepted|processing`. Unknown payment/refund results or refund review block all erasure as `FINANCIAL_RECONCILIATION_REQUIRED`. Paid history additionally requires explicit `GIFTS_FINANCIAL_RETENTION_POLICY_VERSION` and `GIFTS_FINANCIAL_RETENTION_DAYS` (1–36500); no legal retention duration or issuing jurisdiction is supplied by the application. Missing policy yields `FINANCIAL_RETENTION_POLICY_REQUIRED` before another domain is erased. Accounts without paid history need no financial archive.

The successful preflight durably freezes its policy and archive before private deletion starts. Retention begins at that preflight, and later policy changes do not change its expiry. Erasure deletes original commerce rows, operator rows owned by that account, gifts, notes, snapshots, source/AI context, private ledger descriptions, and other account records. The separate archive contains only explicit financial IDs, amount/currency, provider bindings, verified evidence hashes, original ledger linkage, units, and timestamps. It contains no private note, person/profile, conversation, launch URL, session or credential. The completed deletion receipt explicitly returns `financialRetention:{status:'retained',archiveId,policyVersion,retainUntil}` or `{status:'none'}`; retained financial records must not be represented as completely deleted. The pre-deletion account export includes the currently configured retention policy. The existing Gifts worker purges erased accounts' due archives at most once per minute; archives cannot be purged early or from a restored isolated target.

Use the dedicated local CLI after compiling: `node dist/commerce-ops.js ACTION COMMAND_UUID ACCOUNT_UUID payment|refund ORIGINAL_OPERATION_UUID REVIEWER REASON_CODE [DELETION_REQUEST_UUID]`. It requires `GIFTS_OPERATOR_ENABLED=true`, an independent 64-hex `XIJIE_FINANCIAL_OPERATOR_TOKEN`, and the same token in an absolute `GIFTS_OPERATOR_CREDENTIAL_FILE`. Restrict the file to the operator on Windows; POSIX group/other permissions, symlinks and nonregular files are rejected. Never pass credentials as arguments or put them in product UI. Reviewer and reason are bounded stable labels, not freeform customer details.

- `read` records an audit and returns safe operation/job metadata. `recheck` (`retry` alias) inspects the original started operation through its frozen gateway/merchant. It never starts another payment/refund, resets worker attempts/errors/deadline, or accepts an operator's paid assertion. Each operation has at most 10 cumulative manual inspections, including unknown/failed inspections. Reusing an accepted command UUID is idempotent; changed input conflicts. Running commands that lose their reply remain auditable; use a new command UUID for another bounded inspection. Unknown provider outcomes can still require provider/manual investigation after those limits.
- `cancel_unstarted` only closes an undispatched blocked payment whose durable `started_at` is absent. Started or uncertain operations cannot be canceled locally as if no charge occurred.
- `refund_approve` only approves an existing unstarted `review` refund if every original issued paid unit is again available. It reserves those exact lots and dispatches the original refund operation once. `refund_reject` records a reviewed rejection and releases no invented money. Consumed assets and unknown refunds cannot be manually marked refunded.
- For an accepted deletion's unresolved transaction, pass that account's `DELETION_REQUEST_UUID`; only its pending, accepted/processing/failed deletion context permits financial settlement, without restoring sessions or unrelated account writes.
- `retention_read COMMAND_UUID ARCHIVE_UUID REVIEWER REASON_CODE` reads the minimized archive with its own permanent audit. `purge_retention COMMAND_UUID REVIEWER REASON_CODE` purges only due archives of already erased accounts and writes an account-free count audit.

Restore preserves reviewer, accepted action/key/hash, source operation, spent budgets and completed outcomes. It blocks active operator leases, all nonsucceeded reconciliation jobs and archive purge behind irreversible recovery flags; CLI, callback and ordinary workers cannot revive them. Restored copies need a separately reviewed release/migration procedure and current deletion/revocation checkpoints.

## Explicit synthetic issuance

There is no normal signup grant or public issuance endpoint. The nonproduction CLI additionally requires `GIFTS_TRIAL_ISSUANCE_ENABLED=true` and exact account UUID membership in `GIFTS_SYNTHETIC_ACCOUNT_IDS`. Invoke `dist/grant-trial.js ACCOUNT synthetic-trial-v1:CASE POSTAGE VOUCHERS INVENTORY_JSON` after loading private local configuration. The explicit amounts are bounded to 0–1000 each; the named `synthetic-trial-v1` policy and durable grant key are recorded. Reusing the key with changed amounts conflicts. Test users and ordinary users are never inferred from display names or phone-number shapes. These gates are developer test controls and are absent from product UI.

## Rights and validation

The independent rights credential and Identity request context authorize `/internal/v1/accounts/{id}/data-export`, `/erase-preflight` and `/erase`. These work after gift/return permission withdrawal. Export covers exact lots, ledger entries/transactions, delivery/received snapshots, generation context and provenance, projection jobs, notifications, their source events and mutation receipts, with a stable revision and an explicit 20 MiB ceiling. Erasure locks and fences the account and deletes these original facts, all jobs and Outbox in one transaction, then records the minimal receipt and any explicitly retained financial archive reference described above. Late worker writes and new grants cannot cross the fence. Recovery validates ledger/source/received/job/card/notification references and quarantines executable work; restoring a backup does not authorize restarting old model tasks.

Use `node node_modules/typescript/bin/tsc -p tsconfig.json` to compile in this service directory. `XIJIE_TEST_DATABASE_URL` points `node --run test` at a disposable schema on the dedicated local database. Tests create and remove only their random schema. They use real PostgreSQL constraints/locks and Nest routes with synthetic dependency contexts; provider tests intercept the actual SDK transport. Implementation and these checks are complete for this slice, while real OpenAI, original-page and native recovery acceptance are still being verified by the root task. These fixtures do not establish end-to-end acceptance. No source account is modified by the suite.
